# Contributing to `chem-pfd`

Thanks for helping. This document covers the setup, the checks that have to pass,
and — more usefully — the four things about this codebase that a new contributor
will otherwise get wrong.

## Setup

Python 3.10+ (CI tests 3.10 – 3.13). From a checkout:

```bash
pip install -e '.[dev]'          # pytest, ruff, mypy
pip install -e '.[dev,pdf]'      # ...plus cairosvg, if you need PDF/PNG export
```

The package itself has **zero runtime dependencies** and must stay that way:
`pfd/` may import only the Python standard library. `cairosvg` is optional and is
imported lazily inside `Flowsheet.render()`, only when the output path ends in
`.pdf` or `.png`.

Optionally install the commit hooks, which mirror the CI lint gates:

```bash
pip install pre-commit && pre-commit install
```

## The gates

All four must pass; CI (`.github/workflows/ci.yml`) runs the same four.

```bash
python -m pytest -q                 # tests (CI: pytest -q on 3.10/3.11/3.12/3.13)
python -m ruff check .              # lint the whole tree
python -m ruff format --check tests # tests/ must stay ruff-formatted
python -m mypy pfd                  # type check (blocking, not advisory)
```

`ruff format` is enforced on `tests/` only — the rest of the tree is linted but
not auto-formatted, so don't reformat `pfd/` in a feature PR.

Keep a PR to one concern. If a change touches rendering, say so and show what
moved (see *Goldens* below).

## 1. Symbols come from the vendored stencils, never from hand-editing

`pfd/render/_vendored_symbols.py` is **generated**. Its first line says so:

> `"""draw.io-derived equipment symbols (Apache-2.0). GENERATED by
> scripts/vendor_symbols.py — do not edit by hand. ..."""`

Take that literally. The file is regenerated wholesale, so a hand edit is lost
the next time anyone runs the generator, and the drawing silently reverts.

The pipeline is:

```
scripts/vendor_data/drawio/*.xml     mxGraph stencil XML, vendored from jgraph/drawio
        │
        ├── scripts/mxgraph_to_svg.py      stencil XML -> plain SVG
        │
        └── scripts/vendor_symbols.py      KIND_MAP: (kind, variant) -> stencil shape + ports
                    │
                    ▼
        pfd/render/_vendored_symbols.py    generated; registered last, overriding
                                           the hand-drawn defaults of the same kind
```

To add or change an equipment symbol:

1. Add an entry to `KIND_MAP` in `scripts/vendor_symbols.py`, naming the stencil
   file, the shape, and where each port lands. A port is either a named draw.io
   `<constraint>` anchor (`"W"`, `"E"`, `"N"`, `"S"`, …) or an explicit
   placement on a bounding-box edge.
2. Regenerate:

   ```bash
   python scripts/vendor_symbols.py
   ```

3. Review it visually — `python scripts/symbol_sheet.py out.svg` draws every
   registered `(kind, variant)` in a labelled grid with a red dot on each port
   anchor. It is a dev tool, not part of the package.
4. Commit the regenerated `_vendored_symbols.py` along with your `KIND_MAP`
   change. Never one without the other.

Only a handful of symbols are hand-drawn in `pfd/render/symbols.py`: the
Feed/Product boundary flags, the variable-port Mixer and Splitter, and the
ISA-5.1 instrument balloons. Those are original primitives, not stencils. New
*equipment* should come from the stencils so the sheet stays visually
consistent, and so `NOTICE` remains the whole attribution story.

## 2. Every port must land on drawn ink

A nozzle floating in whitespace produces a stream that visibly fails to touch
its equipment. `tests/test_symbol_invariants.py` enforces this over **every**
registered `(kind, variant)` — not just the ones the examples happen to use. It
checks that:

- the symbol SVG parses and declares a `stroke-width`;
- every port, and every alternate face in `port_alts`, lies inside the symbol's
  declared bounding box;
- every port and alternate is within `GEOM_TOL` (2 units) of the nearest drawn
  stroke — the SVG primitives are flattened to line segments and the distance
  measured;
- no two *different* ports resolve to the same point, which would stack two
  streams on one pixel.

If that suite fails on your symbol, **move the port onto the geometry**. Adding
the symbol to `_KNOWN_GEOMETRY_GAPS` or `_KNOWN_DUPLICATE_PORTS` is not the fix,
and a PR that does it will be sent back. Those sets exist to fence off three
pre-existing, *deliberate* cases (the pump and compressor suction nozzles, which
sit in the mouth of an opening the casing is drawn around), and
`_KNOWN_DUPLICATE_PORTS` is empty — keep it empty.

The one legitimate escape hatch is `Symbol.free_ports`: an instrument balloon is
a circle, so its signal connections genuinely have no face of their own and are
allowed to offer the same faces as each other. Free ports are still checked
against fixed ports. Equipment nozzles are never free — a drum's liquid draw is
on the bottom because gravity put it there.

## 3. Goldens: a changed golden means changed rendering

`tests/golden/*.svg` are committed SVG fixtures — one per fixed scenario — and
`tests/test_golden.py` renders each scenario and compares. They are *source*,
not build output, which is why `.gitignore`'s blanket `*.svg` rule carries a
`!tests/golden/*.svg` negation.

The comparison runs on normalized text (`_normalize` canonicalizes the
`<defs>` ordering, which depends on the process hash seed and on nothing about
the diagram). Every other line compares verbatim, so a real regression fails.

After an *intentional* rendering change:

```bash
PFD_UPDATE_GOLDEN=1 python -m pytest tests/test_golden.py -q
```

(on Windows PowerShell: `$env:PFD_UPDATE_GOLDEN=1; python -m pytest tests/test_golden.py -q`)

Then **read `git diff tests/golden/` before committing**. A golden diff is the
diagram changing for every user, so the PR has to say what changed and why — a
deliberate layout, routing or styling decision, with the before/after visible.
"the test was red" is not a reason. If you cannot explain the diff, you have
found a bug, not a golden that needed updating.

`tests/golden/README.md` explains why the fixtures are rebuilt inline in
`test_golden.py` rather than by running `examples/*.py` — those scripts write
into `examples/`, and `03`'s title block would stamp today's date into the
fixture. Read it before adding a scenario.

## 4. Port geometry goes through `pfd/portgeom.py`

Layout, routing, and rendering must never compute a port position independently.
They all call into `pfd/portgeom.py`, which is the single source of truth for a
unit's resolved size and its port coordinates.

This is not style. The bug it prevents actually happened: the renderer forgot a
mirror flip that the router had applied, and every mirrored unit's streams drew
visually detached from their nozzles. One function, three consumers, no way to
disagree.

So:

- `resolve_size(unit)` — the intrinsic `(w, h)` of a unit's placed box.
- `symbol_to_box(...)` — maps a point from the symbol's own coordinates into the
  placed box, applying mirroring **first** and then the clockwise quarter turn,
  which is exactly the order the renderer's SVG transform composes in.
- `port_point(unit, frame, name)` — where a stream visually attaches.
- `port_anchor(unit, frame, name)` — the routing anchor, projected onto the
  bounding-box edge, plus the outward direction.
- `unit_box(unit, frame)` — the true drawn bounding box the router treats as an
  obstacle.

Every one of these takes the resolved box explicitly rather than reading
`unit.frame`, so the same code works during layout (on a `_Slot`) and afterwards
(on a `Frame`). If you find yourself writing `frame.x + something` to find a
nozzle, stop and use `portgeom`.

The related invariant on the geometry model: `Pin` is *intent* (written only by
`Unit.pin()`, never by the engine) and `Frame` is *result* (written only by the
layout engine). The solver reseeds from `Pin` on every run, which is what makes
`layout()` idempotent. Don't write coordinates back onto a `Pin`.

## Examples and the gallery

`examples/*.py` are runnable scripts and are checked by `ruff`. They render into
`examples/` (gitignored). The gallery under `docs/gallery/` is generated by
running them and copying the output — see `docs/gallery/README.md`. If you add
an example, add it to the gallery in the same PR, and consider adding the
scenario to `tests/test_golden.py`.

## Reporting a bug

Include the flowsheet that reproduces it — the topology is usually 15 lines —
and the SVG you got. `fs.validate()` returns the engine's own findings (errors
first, then warnings) and is often the fastest way to describe what went wrong.
